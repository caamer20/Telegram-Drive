# Portable encrypted organization backup

**Design for a future release.** A user moving to another device should be able to restore collections, memberships, tags, favorites, pins and saved searches for the same Telegram account. The first version would write a passphrase-encrypted local document through the platform file picker. In the UI, call it **Export organization** and state that file contents stay in Telegram. The format and limits below are proposed release contracts.

## What crosses the device boundary

| Include in the encrypted manifest | Source and import rule |
| --- | --- |
| Verified owner ID and a portable file reference | Bind to the account captured at export. A reference is the tuple of owner, Saved Messages or numeric channel, and message ID. Use canonical decimal strings for identifiers across JavaScript and Rust. Two channels may contain the same message number. |
| Collections, optional cover and membership edges | Export typed collection records and edges from the account's SQLite workspace. Preserve stable IDs, name, color and icon. Validate covers and membership by their full file reference. |
| Tags, favorites and pins | Export affirmative organization and tag associations, including effective flags from legacy file metadata where the account's store uses them. Preserve display spelling and follow the store's uniqueness rules. An absent entry has no deletion semantics. |
| Saved searches | Preserve name, stable ID, query, supported filter values, tag list, scope, favorites flag and references to imported collections. Validate each filter against the shipping search schema. |

The exporter uses an explicit allowlist and one consistent SQLite read transaction. Generic record blobs, inventory and scan cursors, offline payloads and pack jobs, playback history, transfer and sync queues, device paths, local endpoints, thumbnails and indexes stay on the device. The existing encrypted settings-backup and vault-recovery workflows keep their own readers. Supporter credentials, recovery codes, signed entitlements, sessions, API keys and vault material have no fields in this format. Inspect the native [workspace models](../app/src-tauri/src/workspace/store.rs), [owner lifecycle](../app/src-tauri/src/workspace/account.rs) and [envelope policy](../app/src-tauri/src/crypto/policy.rs).

## File and reader contract

1. Encrypt one typed UTF-8 manifest with the existing standalone passphrase-slot TDENC2 writer. Use its fresh file UUID, salt, data key, chunk authentication, header authentication and final length/digest record. Record the organization purpose inside the authenticated payload. Use a generic suggested filename and neutral envelope metadata so filenames and account/collection names need not appear outside the encryption. A distinct filename extension is for discovery only.
2. Manifest v1 requires a purpose tag, schema major/minor, minimum reader version, required capabilities, export ID, source owner and typed arrays for the graph. Sort records by kind and ID and edges by their full keys for reproducible comparisons. A fresh export always uses new encryption randomness. Preserve existing record IDs across exports; a random export ID is never the identity of a collection.
3. Before expensive work, enforce the envelope reader's format, length, key-slot and KDF parameter bounds. As initial product limits, propose 64 MiB of manifest plaintext, 100,000 combined records and edges, 64 KiB per record and at most 16 levels of nesting. Confirm these limits with a representative corpus and the lowest-memory supported device before freezing v1. Use bounded parsing. Reject duplicate IDs with inconsistent values, dangling collection references, invalid IDs, commands, path fields and unexpected required capabilities. Disallow compression and embedded payloads in v1.
4. Require a fresh export passphrase and confirmation. Confirm the full written output can be read and authenticated before reporting success. An offline attacker can guess a weak passphrase, so explain passphrase loss and strength at export. The existing TDENC2 implementation is alpha; the reader, writer, abuse bounds and temporary-data handling require security review before release.
5. Use owner-private storage for encrypted staging and bounded memory for plaintext. Avoid writing plaintext export files, temporary SQLite journals of the manifest, clipboard content or diagnostic dumps. Desktop publishes the fully verified temporary output into a newly selected destination. Where a document provider cannot guarantee atomic rename, write a new document, close and reopen it to verify, and identify any incomplete output after cancellation. Preserve the last good backup.

## Preview, merge and recovery

1. Select the file, authenticate the entire envelope and final record, then validate its purpose and schema before showing any data. Compare the verified session owner with the encrypted owner. Reject signed-out and mismatched sessions. A passphrase proves access to that backup and supplies no authority to operate on another account. An offline restore may use an already verified owner session only if the native guard can establish it. Otherwise wait for sign-in.
2. Build a local preview of additions, identical rows, conflicts, unavailable file references and unsupported optional fields. Show collection and search labels only after successful verification. Never infer a match from a display name or message ID alone. Preserve unavailable file references in an owner-scoped unresolved set. Associate them only when inventory later observes their exact owner/channel/message tuple. This operation has no upload, download, sync, checkout or remote-write side effects.
3. Merge identical IDs and content as a no-op. Union tag and membership edges. Keep existing local scalar values by default and present individual choices to retain local content, use the backup value or keep both for a conflicting collection/search. Equal display names with different IDs remain distinct and visible in preview. For **Keep both**, persist one stable mapping keyed by owner, source kind and ID, and an authenticated canonical content digest. Remap covers, membership and saved-search references consistently. Preserve later local edits on replay. No restore deletes local organization by omission.
4. Tie the preview to the verified account generation, manifest digest, local workspace revision and chosen decisions. If any changes before confirmation, regenerate the preview. Persist encrypted input and a progress cursor only in a bounded private staging area when the user opts to resume. Revalidate owner, authenticate the complete original, and rederive the preview on resume. Discard staged work on cancellation or expiry. Keep the original backup usable.
5. On confirmation, recheck the owner and workspace revision, then atomically apply the approved changes, conflict mapping and import receipt inside the same owner-guarded SQLite transaction. Check and commit the generation under the same lifecycle fence as account replacement. A competing edit must force a fresh preview. Disk-full or interruption before commit rolls back all active changes. A lost success reply after commit reads the receipt and reports the result without replaying. Track resolved conflicts independently from the export ID so identical records from a new export also remain idempotent.
6. Present actual counts, unresolved references and the local destination after commit. For a proposed **Undo this import**, track only rows affected by this import and their before/after values. Restore a previous value only if it still equals the recorded post-import value. Show later edits or newly attached edges as conflicts. Expire undo state under a published retention rule. Never undo remote operations.

## Compatibility and rollout

Ship the reader, legacy fixtures and local verification before enabling export. Give the format a version independent of SQLite's schema and the app version. A future reader migrates supported older logical manifests in memory into its current import model. An older reader may accept a newer minor version only when all required capabilities are known and the manifest explicitly declares any ignorable fields as optional. Warn before dropping optional data. For an unknown major, too-new minimum reader, unknown mandatory field or incompatible filter, stop before mutation and show the required reader or supported upgrade path. Leave the backup intact. Never guess at TDENC1, settings-backup or TDREC2 contents.

Supply independently retained, synthetic golden encrypted files and their logical expected graphs for each supported writer version. Store their test passphrases with the fixtures. New writers must round-trip through every reader they declare compatible. Exercise reader upgrades on a copy of an older workspace and verify previously created settings and recovery files with their original readers. If a release fails compatibility, stop offering the new writer, retain readers for files already produced and ship a forward reader fix. Eligibility for release requires signoff from the workspace, cryptography and platform maintainers.

| Application-boundary acceptance | Required result |
| --- | --- |
| Clean A profile, two channels with message 42, one unavailable file, multilingual labels | Restore A's graph exactly, keep the two files distinct and resolve only the exact missing reference after inventory arrives. |
| Repeat import, re-export unchanged graph, then edit a record locally | First two repeats add zero objects. A later conflicting edit is visible in preview and survives by default. |
| Conflict with a collection cover and saved-search membership | Keep-both creates one stable extra collection, rewires only imported references and remains idempotent after restart. |
| A signs out or switches to B during preview/commit; concurrent edit in A | Abort before commit or finish wholly in A before the switch. B receives zero records. A changed revision requires a new preview. |
| Wrong passphrase, truncated/reordered data, altered header, oversize input, duplicate IDs, newer required schema | Fail before modifying the workspace. Errors distinguish version/size limits from failed authentication without disclosing manifest data. |
| Disk full, cancelled file picker, interrupted write/import, lost success reply, undo after later edits | Preserve the original backup and local data, recover one committed result on restart, and preserve later edits. |
| Desktop-to-desktop and supported mobile document providers, low space and offline inventory | Verify output on reopen, restore organization without creating remote requests or queue entries, and report unresolved files. |
| Active, grace and non-supporter installations | Each can export and restore. Entitlement, checkout and sponsor visibility follow the existing supporter state throughout. |

Start with private disposable fixtures and a small opt-in pilot. Measure successful first restores, exact graph matches, unresolved counts and interruption recovery using aggregate test counts. Any optional product telemetry requires separate privacy review. Defer cloud delivery and cross-device live merging until local restores are reliable and users need them.
